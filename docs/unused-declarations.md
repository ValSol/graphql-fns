# Declarations in `typeDefs`: only what is used

> How `composeGqlTypes` declares only the types and inputs that something in the schema references, which declarations are kept on purpose, and how this is tested.
> Identifiers: `UD…` facts. Marks: ✅ verified by running code or tests; 📖 conclusion from reading the code only.
> How inputs are generated is in [schema-and-resolvers-analysis.md](./schema-and-resolvers-analysis.md) §2 (F-rows).

GraphQL accepts declarations that nothing references, but they make the schema bigger and harder to read, and clients see types they can't use. So every declaration of the generated `typeDefs` is reachable from `Query`, `Mutation`, `Subscription` or `Node`, except the few kept on purpose (UD10, UD11). Example: under `inventory: { name: 'G', include: { Query: { entityManyDistinctValues: true } } }`, with `City.country` an indexed duplex field and `Country.cities` its non-indexed opposite, `typeDefs` declare `CountryWhereWithoutBooleanOperationsInput` (used by `CityWhereInput.country_`) but not `CityWhereWithoutBooleanOperationsInput`.

## 1. How inputs get into `typeDefs`

| ID | Fact |
|---|---|
| UD1 | ✅ An input creator (`InputCreator`, `src/types/inputs/`) returns `[inputName, inputDefinition, childChain]`. `childChain` maps the names of other inputs to `[creator, entityConfig]`; `fillInputDic` calls those creators recursively and stores each definition under its key in `inputDic`. `composeActionSignature` / `composeChildActionSignature` start this for the inputs of every allowed action. |
| UD2 | ✅ A creator returns one declaration, so whoever needs an input gets exactly it. The only definitions with two declarations are pairs where the enum is used by the input: `XSortEnum` + `XSortInput`, `XGeospatialFieldNamesEnum` + `XNearInput`, and the enum + input of `createEntityWhichUpdatedInputType`. |
| UD3 | ✅ `fillInputDicForCustom` finds the input of a custom action argument by searching `^input <Name> {$` / `^enum <Name> {$` in the definitions of all creators of `src/types/inputs/index.ts`, for every entity and representation. If the declaration is found inside another input's definition (UD2), it adds that definition and marks the name with `!<Name>` (excluded from `typeDefs`). |

## 2. Where inputs are chained

| ID | Fact |
|---|---|
| UD4 | ✅ `createEntityWhereInputType` returns `XWhereInput`; `createEntityWhereWithoutBooleanOperationsInputType` (named export of `createEntityWhereInputType.ts`) returns `XWhereWithoutBooleanOperationsInput` (same fields, no `AND` / `NOR` / `OR`) for a tangible entity and `''` for others. It is used only by the relational filters `y_` of other entities. Both chain `YWhereWithoutBooleanOperationsInput` exactly for the fields that get `y_: YWhereWithoutBooleanOperationsInput`: unique or indexed relational and duplex fields, and parent relational fields whose opposite is indexed; and `EWhereInput` for indexed embedded fields. |
| UD5 | ✅ `createEntityCreateInputType.ts` has a creator per declaration: `createEntityCreateInputType` (`XCreateInput`), `createEntityCreateChildInputType` (`XCreateChildInput`, used by non-array relational / duplex fields pointing to X), `createEntityCreateOrPushChildrenInputType` (`XCreateOrPushChildrenInput`, used by array ones), and the factories `createEntityCreateThruFieldInputType(y)`, `createEntityCreateThruFieldChildInputType(y)`, `createEntityCreateOrPushThruFieldChildrenInputType(y)` that return the creator of a `Thru` input of field `y` (memoized per field name, so the same name gives the same function; `''` if `y` is not a required duplex field of the entity). `getChildInputNameAndCreator(config, array, oppositeRequiredName)` gives the name and creator of the input of a relational or duplex field; create and update inputs use it both for the field type and for `childChain`, so they always match. `XCreateThru_y_FieldInput` has the fields of `XCreateInput` except `id`, and `y` is optional. |
| UD6 | ✅ `fillEntityTypeDic` adds `XConnection` (and so `XEdge`) of an embedded entity only for array embedded fields with `connection` in `variants`, the only place `createEntityType` uses it (`xThroughConnection`). |
| UD7 | ✅ `composeGqlTypes` builds geospatial declarations last and passes `composeGeospatialTypes` the rest of `typeDefs` (interfaces, entity types, inputs, `Query`, `Mutation`, `Subscription`, custom actions included). Called without the second argument, `composeGeospatialTypes` returns everything. |
| UD8 | ✅ `composeGeospatialTypes(generalConfig, typeDefsToUse)` keeps the common inputs (UD10) and every other geospatial type or input referenced in `typeDefsToUse` or by an already kept declaration (e.g. `GeospatialPolygon` → `GeospatialPolygonRing` → `GeospatialPoint`, `GeospatialMultiLineStringCorridorInput` → `GeospatialLineStringInput`). |
| UD9 | ✅ A geospatial field with `geospatialType: 'MultiLineString'` is created / updated with `input GeospatialMultiLineStringInput { lineStrings: [GeospatialLineStringInput!]! }`, the shape expected by `multiLineStringFromGqlToMongo` and returned as `GeospatialMultiLineString`; like other non-common geospatial inputs it is declared only if referenced (UD8). Create, update and read through the schema are tested in `multiLineStringThroughSchema.mtest.ts`. |

## 3. Kept on purpose

| ID | Fact |
|---|---|
| UD10 | ✅ `GeospatialPointInput`, `GeospatialPolygonRingInput`, `GeospatialPolygonInput`, `GeospatialMultiPolygonInput` are declared whenever there is a geospatial field, used or not. They are in `commonInputTypes` of `fillInputDicForCustom`, which skips them as always available, so custom actions may use them without any field referencing them. |
| UD11 | ✅ Every enum of `generalConfig.enums` is declared as `XEnumeration`, used or not, because manually created actions (type definitions written next to the generated `typeDefs`) may use it. `fillInputDicForCustom` also relies on it: it skips an argument `XEnumeration` whose enum is in `generalConfig.enums`. |
| UD12 | ✅ Custom actions: `createEntityCreateChildInputType`, `createEntityCreateOrPushChildrenInputType` and `createEntityWhereWithoutBooleanOperationsInputType` are in `src/types/inputs/index.ts`; `fillInputDicForCustom` also tries the `Thru` creators of every required duplex field of the entity (`composeCreateThruFieldInputCreators`). A custom argument `XWhereWithoutBooleanOperationsInput`, `XCreateChildInput` or `XCreateThru_y_FieldChildInput` adds exactly that input and its children, under its own name, without `!<Name>` (tested in `src/types/unusedDeclarations.test.ts` and `fillInputDicForCustom.test.ts`). |

## 4. Tests

| ID | Fact |
|---|---|
| UD13 | ✅ `findUnreachableDeclarations(typeDefs)` (`src/test/findUnreachableDeclarations.ts`, test helper) builds the schema with `buildASTSchema(parse(typeDefs))` and walks from `Query`, `Mutation`, `Subscription` and `Node`: field types and arguments of object types and interfaces, interfaces of a type, implementations of an interface (so every type implementing `Node` is reached), members of unions, field types of inputs. It returns the names it did not reach, except built-in scalars and the declarations every schema has on purpose: `DateTime`, `Upload`, `Node`, `RegExp`, `SliceInput`, the common geospatial inputs (UD10) and the enums `XEnumeration` of `generalConfig.enums` (UD11). Because of `buildASTSchema` it also throws if `typeDefs` references an undeclared type. |
| UD14 | ✅ `src/types/unusedDeclarations.test.ts` asserts `findUnreachableDeclarations(typeDefs)` is `[]` for a config with indexed and non-indexed relational and duplex fields, a required duplex field (`Thru` inputs), parent relational fields with indexed and non-indexed opposite, indexed embedded fields with `connection` / `count` variants, non-array embedded field, indexed `Point`, non-indexed `Polygon` and `MultiLineString` fields, an indexed enum field: under the full schema, under an `inventory` with a single action for every root and child action, with a representation (full and with a single representation action), with custom inputs and with a single custom action whose arguments are `CityWhereWithoutBooleanOperationsInput`, `CityPeriodInput` (custom input), `CityCreateChildInput` and `CityCreateThru_country_FieldChildInput`. The `copy…` actions are tested on a second config with clones (`Menu` / `MenuClone`), full and with every single action. |
